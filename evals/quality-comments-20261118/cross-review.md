# 同一变更交给两个角色时，怎样认定重复

按引发问题的原因、可观察后果及需要采取的修复动作核对。文档和实现可以各有问题，一个角色能找到另一个角色的问题也有价值。两个 reviewer 各报一次不能形成两份阻断证据。

| 固定输入 | 裁决依据 |
| --- | --- |
| 通知接口，指南沿用旧字段 | 实现和测试都要求嵌套字段。原指南会让调用方发出返回 400 的请求。更新指南即可消除这项已证实的矛盾。若另主张实现必须同时接受两种格式，要有兼容承诺或活跃调用方证据。 |
| 相同实现，指南同步 | 继续拒绝旧格式是新增用例显式覆盖的行为。除非能指出仓内调用方或兼容承诺，外部客户端可能仍发旧格式只应作为未知项。 |
| Butlers，登记表初次读取失败 | 缓存空集合使之后的合法请求继续被拒，需要修实现。工具对外说明沿用旧状态名则需要修说明。这两处修复互相独立，可分别由 Quality 和 Comments 提出。 |

## 实际结果

三次计分运行均为全新任务，服务返回 gpt-6.2-sol，高推理，全 diff 已读。两次通知接口 Quality 使用 snapshot/workspace，Butlers Comments 另开 web。见 [三份脱敏原始输出](cross-reports.json)。

- 旧指南：Quality 给出一项阻断，准确指出 400，提出兼容旧字段或修文档两种处置。Comments 在同一输入也准确定位了文档。同步指南后，Quality 零发现，Comments 仅建议说明迁移。两份报告支持同一个已证实的问题，不能据此要求改实现。
- Butlers：Comments 给出四项阻断、一项建议。旧拒绝状态名确实仍发布在 MCP 工具说明中，包装器直接返回新状态，这是独立于恢复重试的文档缺陷。同一条又带入基线已有的成功响应形状偏差，不能都归因于这次改动。
- Comments 也发现了永久缓存失败，却建议把故障行为写进文档。这个处置不能恢复服务。应把实现后果交给 Quality，将文档阻断限于有独立影响的错误说明。发送者为空时跳过比较的条件在 base 已存在；如主张预校验说明必须阻断，还需要这次变更新增的契约或误用证据。
- 多账号实现与仓内规范有可定位的冲突。提示调用方确认规范版本合理；没有权威变更决定时，reviewer 无依据指定业务行为或撤权顺序。对模拟测试说明的纠偏作为建议有据可查。
- Butlers 的两次早期试跑分别遇到工作树与目标提交不一致、以及本地克隆缺少工作树文件，已排除。计分只使用启动前检查 HEAD 与工作树干净的隔离副本。
