# Quality 与 Comments 的 6.2 回放

2026-11-18。建议保留两个角色，各自收紧阻断条件。评审结论供调用方裁决。正式角色提示词、调用 skill 和 Decision API 均未改动。

本轮共 16 次计分调用，9 次 Quality、6 次 Comments、1 次同输入 Performance。服务实际返回 gpt-6.2-sol，推理等级 high，各报告均读完全部 diff。两个早期工作区与提交不匹配的试跑已排除。这 16 次累计 4,606,589 个 provider 计数 token，含重复上下文。历史 Performance 结果只用于参照。按根因及修复动作裁决，分别记录命中、复报、严重度和角色归属。

## 建议的最小调整与验收

1. **Quality。** 给阻断增加一个问题：本次改动让哪个已知调用方、受支持输入或恢复路径发生了什么后果？测试本身可以阻断，但要指出被遮住的具体回归或失效的必要验证。把“代码仍可更好”与“这版会留下已证实故障”分别表述。
2. **Comments。** 阻断时同时给出已有文字、可验证的契约、照做后的后果及文档修改处。遇到未决产品行为或疑似实现缺陷，明确谁需确认，以及修文档后哪个问题仍存在。避免把历史文档偏差附在新增阻断下。保留错误请求与错误配置文件名这两个阻断锚点。
3. **主控。** 多个角色给出同一根因、后果和修复动作时合并。独立设计缺陷和错误使用说明分别保留。单个 reviewer 工作时仍可以提醒调用方发现的相邻问题。
4. **结果可用性。** 清理建议中不可见的控制字符，并用确定性检查拦住损坏的可复制文本；提示词只能辅助。给外部查询设置停止条件，把性能开销另记，避免用累计 token 推算费用。
5. **下一轮验证。** 固定 6.2、工具与版本，分别改一个角色。先重跑错误缓存/修复、旧测试 ID、指南 400/201、MCP 配置与重启对照；再给每个角色一个未参与调词的变更。接受条件是保住真实阻断、修复目标不复报、未经证实的兼容或旧债不再升为阻断，并能直接使用替换文本。

这是有意挑选的小样本，每个角色与输入组合只跑一次。适用于定位失败模式，不能估算线上命中率。探针用真实函数及本地替身验证特定路径，没有模拟生产流量。
