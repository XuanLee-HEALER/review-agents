# 独立交叉验收

由主控另行准备，同一代码变更同时引入两个需要独立修复的缺陷。评分标准在评审前冻结，样本内容未提供给角色提示词的维护者。

- A：明示零次重试却调用发送器三次，Quality 应指出并阻断。公开成功回执改名，而指南示例仍读取旧字段，Comments 应定位旧示例、指出读出 undefined 和修文档的位置。仅更新文档无法恢复零次重试的契约。若 reviewer 另提必须为外部调用方保留旧响应字段，应核对兼容承诺。
- B：恢复零次重试，文档示例同步。上述两项均不得复报。没有证据的外部兼容性也不能阻断。
- 主控裁决时，零次重试违约与示例过期需要分别关闭。多个 reviewer 指出同一个请求或回执问题仍只派一项修复。

复现时将一个尚不存在的临时目录传给 `python3 prepare.py`。脚本为两个固定提交建独立检出，分别运行真实函数并从 README 提取示例字段核验。原始变更和修复使用同一 base。

实际运行见 [首个构建](v1.json)、[中间提示词](v2.json)、[增加事实预算前](v3.json) 与 [最终组合](v4.json)。四个最终报告均读完整 diff。A 的发送器实测执行三次，Quality 阻断成立；Comments 同样指出文档的“一次”承诺失效，单列交给实现负责人确认，明确只改文字仍会重试。主控将两份报告合并为一次实现修复。读取旧属性得到 undefined，Quality 和 Comments 各报一次，主控按一处回执示例问题处理。Quality 的标题偏向保留旧属性，它的建议也允许迁移并同步指南；单凭本仓示例无法确定外部兼容义务。B 实测发送一次且示例得到正整数，Quality 零发现，Comments 仅建议加迁移说明。四份报告各自的角色提示词、构建摘要与服务实际模型存于 JSON。
